# Buddy meal logging in ChatGPT and Claude

Reviewed design · November 19, 2026 · Based on main at `88e9005`

## The experience

Either buddy can describe a meal once in their usual assistant and record what each person ate. For example, “The dal made four equal servings. I ate one and Jamie ate one and a half. Log dinner for both of us.” If the whole pot contains 1,200 kcal and 60 g protein, the entries should be 300 kcal and 15 g for the cook, and 450 kcal and 22.5 g for Jamie. The remaining food stays unlogged. The assistant can do the same when Jamie cooks and her buddy has given her permission.

| What the person says | Expected result |
|---|---|
| “Log dinner for both of us.” Both portions and the intended buddy are clear. | Show the two portions and their nutrition, then save both as one operation. A clear request to log the reviewed portions is sufficient. Return one receipt naming both people and their portions. |
| “I already logged my lunch. Jamie ate half as much. Log hers.” | Reuse the selected lunch entries, using half the **logged plate** as the reference. Add only Jamie’s entry. |
| “I cooked this for Jamie. She ate 250 g of the 1 kg cooked batch. Log hers.” | Save 25% of the batch to Jamie’s diary. The cook needs no entry. |
| “I made dinner for us.” | Preparing a dish supplies recipe information. Ask who actually ate it and how much before saving. |
| The buddy has not granted direct logging, or a portion is unknown. | Explain what is missing. Offer the existing send-for-review workflow or self-only logging. Let the cook choose before changing either diary. |

## Implementation

1. **Give each recipient control.** Add a default-off switch to the signed-in person’s Buddy settings, worded “Let [name] add meals to my log.” Store a directional grant bound to the accepted relationship. Each person can enable or revoke their own grant independently. Ending the relationship ends both grants. Reconnecting as buddies starts with fresh consent. The grant covers adding food entries only. Keep normal proposal sharing available even when delegation is on.
2. **Make the recipe and serving basis explicit.** Extend the shared meal preparation service to accept a known whole-recipe total, known nutrition per serving, or the existing ingredient estimate. Preserve supplied nutrition and distinguish estimated values, known zeroes and missing values. The preview records the reference amount (e.g., four equal servings or 1,000 g cooked) and calculates each person's portion on the server. Use cooked yield for weight-based splits. Ask for the missing conversion if the user mixes cups and grams. For meals with different sides, use the relevant items and quantities per person. Round for display only. A small serving such as one eighth of the pot must work even though the current meal-library multiplier starts at one quarter. Actual intake can leave leftovers.
3. **Expose one dedicated write tool on the existing MCP.** A proposed `log_buddy_meal` takes an actor-owned source (signed preview, saved meal, or selected logged entries), one explicit accepted buddy and the portions to create. The normal self-only tool stays available. When the source is an existing log, default to adding only the buddy. Resolve names to accepted buddies and clarify ambiguity. Bind the commit to the reviewed meal, the versions of any editable source records, recipients, portions, meal type and date. A preview is valid only for the user who prepared it. If exact inputs and permission are already clear, avoid a redundant confirmation turn. Let the existing buddy lookup report whether the caller may add meals for each buddy.
4. **Check authority and commit once.** Require a new, separately consented OAuth permission for adding buddy meals, alongside the relevant existing source access and self-write permission when saving to the cook’s diary. Recheck the accepted relationship and the recipient’s grant inside the write transaction, with locking that also covers revocation and buddy removal. Save a separate, recipient-owned batch for each plate and the operation receipt in one transaction. Use deterministic lock order across accounts. A failed two-person request writes neither batch. Bind retries to one operation ID and the approved inputs. Reject reuse with changed inputs. Prevent an already consumed preview from creating a second self portion through either the old or new tool. After removal or correction, a retry must never recreate or overwrite the entry. A receipt should distinguish what was originally saved from current state and disclose only what the caller may see.
5. **Make the result visible and correctable.** Show “Logged by [buddy]” in the recipient’s daily log and own assistant reads. Store attribution with the batch, independently of the grant, so removing a buddy preserves diary history. Each owner can correct or remove their own portion, including after revocation. Undoing the cook’s plate leaves the other plate intact. Reuse NutriTracker’s sharing projection for selected food and nutrition fields; keep unrelated free text, private profile fields and other diary entries out of transferred data and write receipts.

### Details to resolve in the implementation

- Today's proposal tool accepts saved meals or existing log entries. Extend its source resolver to accept the cook's reviewed recipe preview, so sending a fresh recipe for review never requires the cook to invent a personal meal. Keep proposals pending until the recipient accepts.
- Today's batch undo is owner-scoped and time-limited. Add the new batch type to the owner's existing undo path and preserve that window. Keep normal owner entry corrections and removal available afterwards. Do not give the cook access to the buddy's edit or delete tools.
- Check authorization before returning any cached receipt containing buddy details. After revocation, a retry may acknowledge the cook's earlier operation without returning the buddy's current records. Using the original request ID after a successful save must never post again.
- For a measured batch, clarify if the allocations exceed the yield (e.g., five portions claimed from four). This check applies to the whole batch; a buddy can eat more than the cook when an existing plate is the reference.

## Review and release checks

| Risk found in review | Acceptance check |
|---|---|
| A general buddy connection accidentally permits writing in both directions. | With two test accounts, enable A → B only. B → A, an unrelated account, a pending buddy, and an assistant with only the old scopes all fail to post. Repeat with the roles reversed. |
| The assistant scales the whole recipe as though it were one plate or guesses what someone ate. | Run the dal calculation above, one eighth of a pot, an already-logged plate, unequal side portions, and a missing cooked yield. Compare both diaries with the expected quantities. Confirm supplied label values survive preparation. |
| A timeout, partial save, or change of mind creates the wrong records. | Force failure between the two writes, retry the same request, retry after an owner’s correction or deletion, and exercise old/new tool reuse of a preview. For editable sources, a changed portion between preview and save requires a fresh review. |
| Concurrent removal, reciprocal writes, or switching assistants breaks isolation. | Race revocation/removal against a save and exercise simultaneous A → B and B → A. Verify relationship and grant checks at commit, zero partial writes, independent owner correction, and no access to private buddy totals. Distinct new chat requests are separate intentions; check recent history when a person asks whether an uncertain save landed. |
| Existing sharing starts posting directly or a pending proposal is logged twice. | Retain a meal-occurrence identifier across proposal and direct posting, separate from a reusable recipe ID. Check the sender's outstanding proposal for that occurrence and recipient. If pending, ask them to resolve it before direct posting. If accepted, return already logged. Exercise concurrent accept and direct-post attempts. Never auto-accept an open proposal or convert “share” into a direct write. |
| A server release passes tests while a phone still has old tools or scopes. | Use one backend release with a reversible feature switch and default-off grants. Run fixture and two-account end-to-end tests first. Refresh the hosted NutriTracker Mobile tool list in ChatGPT and verify Claude discovery. Reauthorize each assistant used for direct logging with the new permission. Verify a shared dinner on both phone clients, recipient attribution, and owner correction before announcing availability. |

### Recommended first release

Ship direct meal creation for an accepted, opted-in buddy, including different servings for the same meal and the already-logged case. Use the existing Buddy page for the one-time grant and the existing diaries for review and corrections. This gives the cook one routine logging interaction while the recipient retains control of their diary. The plan assumes one buddy per request and correction by the diary owner. A later request to edit someone else’s history would need a separate product decision.
